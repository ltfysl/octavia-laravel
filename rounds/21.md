# Round 21 — Fine-Grained API Token Scopes

## Current Product State
Twenty rounds in. API v1 tokens carried only coarse `read`/`write` abilities — a CLI that only starts runs had to hold full write access to prompts too. This round introduced per-resource scopes.

## Selected Goals
1. Per-resource scopes (`prompts:read/write`, `runs:read/write`) with backward-compatible implication rules.
2. Scope enforcement on every API endpoint.
3. Scope documentation in the README.

## Implementation Summary
- **`EnsureTokenHasScope` middleware** (`scope:…` alias): accepts the exact scope, Sanctum wildcard (`*`), legacy `write` (implies everything), legacy `read` (implies `*:read`), and `res:write` implies `res:read`. Resolution goes through `tokenCan()` so mocked/transient tokens behave like persisted ones.
- **routes/api.php**: every endpoint now uses `scope:` instead of `abilities:`; evaluate stays read-scoped, store/cancel stay write-scoped.
- **AuthTokenController**: issuance validates the extended scope set; unknown scopes rejected.
- **README**: scope model + issuance example documented.

## Tests / Validation
- ApiScopesTest (5): prompts:read can read not write; prompts:write implies read; runs:write cannot read prompts; runs:write can start+read runs; unknown scope rejected at issuance.
- ApiV1Test (9, existing): all pass unchanged — legacy `read`/`write` tokens fully backward compatible.
- Full suite: **119 tests / 399 assertions green**. Pint clean, vue-tsc clean, build green, 7 E2E passed.
